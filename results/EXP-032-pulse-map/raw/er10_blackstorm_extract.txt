According to the output, it is the column reporting objects that makes the total add up, and an open event 
is one object opening at one type, so a class contributes as many events as it has objects multiplied by the 
number of types each accepts. Thus, there are 147 open events, 71 distinct objects and 17 classes, which 
means that, in general, there are 17 kernel driver classes that are reachable from a sandboxed application. 
However, the value 71, which is the list of driver objects that we can hold a connection to, is more solid for 
attacking purposes. About the value 147, it is not a count of drivers because it counts connections, which is 
an object opened at one type, and it multiplies the same object up to 16 times. The kernelcache contains 
around 259 user client classes, which are drivers that we can potentially talk to.   
There is a series of specific cases that we could comment on in detail such AppleJPEGDriver, graphic 
drivers, video decoder (AppleAVD), and other ones, but it is out of the context for this article. In general, 
the usual request path is IOServiceOpen function (when the request cross into the kernel) → 
is_io_service_open_extended function (it is a common routine for every driver on the system and when 
the sandbox policy is consulted) → IOService::newUserClient function (the driver could replace with its 
own, but it is where the type-value is examined) → driver client object (and external methods behind it).  
Our real scenario is that we have 17 kernel driver classes that are reachable, but obviously the total 
number of user classes is higher than it (259) and the number of classes registered is much higher than it 
(3360), as it is shown below:
