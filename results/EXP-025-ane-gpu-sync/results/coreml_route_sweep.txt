Core ML placement heuristic — first decision table + a recovered constant (2026-10-10)
=====================================================================================

Machine: Mac17,14 M5 Max, macOS 27.0.1/26A434. Oracle: MLComputePlan via coremltools 9
(harness/coreml_route_sweep.py) — reads the planner's per-op preferred device AND its own cost
weight (MLComputePlanCost.weight). Models are single-op ML Programs built with torch+coremltools.

3. KERNEL DEPENDENCE (H=8, fp16, ne) — the rule is COMPUTE, not shape

  k=3: C=352 (71.4M MACs) CPU ; C=384 (84.9M) ANE
  k=5: C=192 (59.0M) CPU ; C=256 (104.9M) ANE       <- flips EARLIER than k=3

4. BRACKET

  k=3 C=360  MACs 74.6M  FLOPs 149.3M -> CPU
  k=3 C=368  MACs 78.0M  FLOPs 156.0M -> ANE
  k=5 C=216  MACs 74.6M  FLOPs 149.3M -> CPU
  k=5 C=224  MACs 80.3M  FLOPs 160.6M -> ANE
  k=7 C=160  MACs 80.3M  FLOPs 160.6M -> ANE

  Flip lies in FLOPs (149.3, 156.0] M  ->  ~1.5e8 FLOPs. Kernel-size dependent; fp16 only.

FINDING (first cut of the heuristic)
------------------------------------
  - compute_units CAPS the candidate set (cpu->CPU, gpu->GPU, ne/all->prefer ANE);
  - fp16 is a gate: fp32 falls to CPU;
  - a conv is ANE-placed when its estimated work exceeds ~1.5e8 FLOPs (~7.5e7 MACs), and the
    threshold scales with kernel area (k=3 vs k=5 flip at different C), i.e. it is a COMPUTE
    threshold, not a spatial/channel one;
  - at the sizes tested, conv1x1 / pooling / linear did not reach ANE.

CAVEATS
-------
  - single-op models; multi-op graphs add segment/boundary costs the planner also weighs
    (unmeasured here);
  - the ~150 MFLOP bound is a bracket (149.3-156.0M), one OS build, fp16;
  - plan != runtime: this is the planner's decision, not a runtime confirmation (see API-146 for
    the plan/runtime relationship and the ANEXL lens for ground truth).

5. P2 — RUNTIME VALIDATION (does the plan hold at runtime?)
-----------------------------------------------------------
Built a just-below / just-above pair (conv3x3, H=W=8, fp16, cpuAndNeuralEngine):
  route_below.mlpackage  C=352  71.4M MACs  plan = CPU
  route_above.mlpackage  C=384  84.9M MACs  plan = ANE
Ran 20000 predictions each under enginemon (ANEXL lens; harness/coreml_run.py, the ObjC runner
being unusable for these mlprogram models — empty input shape -> E5 buffer alloc failure, so its
first reading was compile-side and discarded):

  arm     predictions   ANEXL U   ANE UP
  below   20000             0        0
  above   20000         12065    12094

=> the planner's decision is HONOURED at runtime: above the ~1.5e8-FLOP threshold the conv runs
on the ANE; below it there is no ANE activity at all. No silent fallback observed for this case.

BUG NOTE: the first P2 attempt used the ObjC coreml_run.m, which built a zero-shape MLMultiArray
for these models (MLE5 "Failed to allocate E5 buffer object"), crashed on the first predict, and
its ANEXL delta was therefore specialization/compile-side, not inference. The Python runner
(harness/coreml_run.py, coremltools) is the correct instrument here.
