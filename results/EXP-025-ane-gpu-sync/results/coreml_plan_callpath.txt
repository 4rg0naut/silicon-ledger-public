CoreML placement code — call path traced (2026-10-10)
=====================================================

Machine: Mac17,14 M5 Max, macOS 27.0.1/26A434. Method: runtime dump of the mapped CoreML image
(harness/coreml_image_probe.m) -> llvm-mc --disassemble (correct bytes; see the address-space
correction below) -> LLM-assisted decompilation via the eval `completion` helper, verified against
the instruction listing.

ADDRESS-SPACE CORRECTION (why the first attempt was wrong)
----------------------------------------------------------
`ipsw dyld disass --vaddr <runtime IMP>` and `ipsw dyld a2s` do NOT share the runtime address
space: a first decompile of 0x191f7ab84 returned BLAS code (cblas_dsymm), and our own runtime dump
of the SAME address begins with a prologue (`hint #27; sub sp,sp,#80; stp ...`). The authoritative
bytes are therefore the ones read from the loaded image at runtime; ipsw remains useful for
extraction and symbol names but its --vaddr space must be mapped first.

TRACED PATH (from the runtime entry points)
-------------------------------------------
-[MLComputePlan computeDeviceUsageForMLProgramOperation:] @0x191f7c2a8
   -> extracts MLProgram op attributes (sub_65403100/65402940/65393152/...)
   -> sub_191F7ADB4(...)      <- cost region (see estimatedCost wrapper)
   -> if non-null: sub_191F7BC30(x20, e, f)   <- builds the device-usage result
   -> returns the result object (or NULL)

-[MLComputePlan estimatedCostOfMLProgramOperation:] @0x191f7ab84
   -> wrapper: builds a cost object via a large helper, extracts a double (sub_65395280),
      NaN-checks it (fcmp d0,d0 / b.vs), formats a string, returns it.

sub_191F7BC30 @0x191f7bc30 (the device-usage builder)
   - `switch (sub_65408860(v0)) { case 1: ...; case 2: ...; case 4: ...; default: return 0; }`
     i.e. a switch on POWER-OF-TWO compute-unit values, each case selecting a distinct string
     constant and sub-path. 1/2/4 -> CPU/GPU/NeuralEngine is the parsimonious reading (bit values
     match compute-unit masks) but the string contents were NOT resolved in this pass.
   - no floating-point comparison; integer sentinel checks (0x7fffffffffffffff) and a bit-mask
     filter (`tst x22, w8`) drive the loops.
   - one double constant is loaded from a data table (adrp+ldr d0,[x9,#3728]) into a struct.
   - builds and returns a dictionary/collection object (or 0).

P3e — CORRECTION: no floating point in this path; structural map (2026-10-10)
-----------------------------------------------------------------------------
CORRECTION to the API-151 note above. The `fcmp d0,#0.0 / b.hi / csel` attributed to the
device-usage path came from an `ipsw dyld disass --vaddr 0x191f7c2a8`, and ipsw's --vaddr space is
NOT the runtime address space (see the correction at the top of this file). On the CORRECT runtime
bytes, `-[MLComputePlan computeDeviceUsageForMLProgramOperation:]` touches no `d0`/`s0` register at
all - it contains ZERO floating-point instructions. Grepping the whole examined cluster (correct
runtime dumps, llvm-mc):

    devuse.rt.asm      fcmp=0  fmul/fdiv=0  fadd=0  scvtf=0   (no d0/s0 access at all)
    cost.rt.asm        fcmp=1  (the single NaN check, fcmp d0,d0 / b.vs, in the estimatedCost wrapper)
    select.rt.asm      fcmp=0  fmul/fdiv=0  fadd=0
    costhelper.rt.asm  fcmp=0  fmul/fdiv=0  fadd=0

So API-151's specific floating-point claim is an artifact and is withdrawn (API-153).

Structural map, from a reverse-reference scan (new tool harness/coreml_findcallers.m: scans the
mapped image's executable segments for BL/B sites whose target is a given address, and readable
segments for 8-byte pointer-table entries):

  * `sub_191F7ADB4` is its OWN function (prologue `sub sp,sp,#432`), not a block of the cost method.
    It orchestrates tag-keyed dictionary lookups over type tags {1,2,4,5,6}, selects one element by
    tag==2, and returns an object - NO accumulation, NO cost comparison, NO float arithmetic.
  * `sub_191F7BC30` (device-usage builder, compute-unit enum switch 1/2/4) is called from
    `0x191f7bb60` and `0x191f7c358` (the latter inside computeDeviceUsageForMLProgramOperation:).
  * `0x191f7c358 -> 0x191f7bc30` (bl -1832) and the method also calls `sub_191F7ADB4`.
  * The ObjC method IMPs (`0x191f7ab84` estimatedCost, `0x191f7c2a8` computeDeviceUsage) have NO
    direct BL callers - they are reached through objc_msgSend, as expected for methods.

Verdict: the functions reachable from the two ObjC entry points are ATTRIBUTE PLUMBING and
per-unit configuration lookup - not the decision. The numeric cost/selection work is delegated to
callees (`sub_65574864`, `sub_65576364`, ...) that have not been read. Reading those callees, or
tracing the plan-assembly path dynamically, is the next pass.
