Core ML placement: SDK-27 plan API, device support info, and the flip point (2026-10-10)
=======================================================================================

Machine: Mac17,14 M5 Max, macOS 27.0.1/26A434. Toolchain: Xcode 27 clang, SDK from
/Applications/Xcode.app (CLT alone is insufficient - env.md). Models: single conv3x3,
generated by harness/make_conv.py with the bench venv (coremltools 9 / torch 2.11).

1. The SDK-27 ObjC plan API (why coreml_plan.m had to be fixed)
---------------------------------------------------------------
`coreml_plan.m` in this pack WROTE WITHOUT ERRORS against the SDK that shipped with the
original run, but does NOT build (and would not run) against the SDK 27 headers present now:

  * there is no `MLComputeDevice` class  -> devices are `id<MLComputeDeviceProtocol>`
    (concrete: MLCPUComputeDevice / MLGPUComputeDevice / MLNeuralEngineComputeDevice);
  * `MLModelStructureProgram.functions` is a NSDictionary<NSString *, Function *>
    (there is no `functionName` property on the function) -> iterate the dictionary keys;
  * the synchronous `+computePlanWithContentsOfURL:configuration:error:` no longer exists;
    the entry point is the async
      +[MLComputePlan loadContentsOfURL:configuration:completionHandler:]
    (with the private `+computePlanOfModelStructure:modelAsset:configuration:error:` behind it).

  * GOTCHA (cost a segfault): the harness builds WITHOUT ARC, so the object handed to the
    completion handler is only borrowed - `plan = p;` leaves a dangling pointer and the next
    `[plan modelStructure]` segfaults (`libobjcMsgSend + 32`). Fix: `plan = [p retain];`.

Both `coreml_plan.m` (fixed) and the new `plan_devicesupport.m` now build and agree:
  ./coreml_plan /tmp/p3b/small.mlpackage cpuAndNeuralEngine  -> CPU   PLAN SUMMARY: CPU=1
  ./coreml_plan /tmp/p3b/large.mlpackage cpuAndNeuralEngine  -> ANE   PLAN SUMMARY: ANE=1

2. Device support info - the decision is a PREFERENCE, not a support gate
------------------------------------------------------------------------
`MLComputePlanDeviceUsage` privately exposes `-deviceSupportInfoArray` and
`-supportInfoForComputeDevice:`; entries are `MLComputePlanDeviceUsageSupportInfo` with ivars
`_state` (int64) and `_computeDevice`. Dumped on both sides of the threshold:

  small (C=256,H=16 -> 1.89e7 conv FLOPs)   preferred=CPU   supported: CPU ANE
      CPU: Support state: 0        ANE: Support state: 0
  large (C=256,H=32 -> 1.21e9 conv FLOPs)   preferred=ANE   supported: CPU ANE
      CPU: Support state: 0        ANE: Support state: 0

Both devices are SUPPORTED (state 0) in BOTH cases; only `preferred` changes. So the placement
preference is not an eligibility/support decision - it is a cost/perf preference taken inside
the framework. The public API exposes the DECISION, and the private support info still does not
expose the comparison. `estimatedCostOfMLProgramOperation:` returns `<MLComputePlanCost>` with
weight=1 for a single-op model (normalised) - also not the comparator.

3. Independent re-derivation of the flip point
---------------------------------------------
Fresh, deterministic oracle (harness/plan_devicesupport.m), single conv3x3:

  C=256, vary H (W=H):
    H= 8  7.55e7  CPU        H=11  1.427e8  CPU
    H=10  1.180e8 CPU        H=12  1.699e8  ANE
                             H=13  1.994e8  ANE
                             H=14  2.312e8  ANE
                             H=16  3.020e8  ANE
  C=256, H=12, vary W (FLOPs proportional to W):
    W=10  1.4156e8 CPU
    W=11  1.5571e8 ANE
    W=12  1.6987e8 ANE

=> for C=256 conv3x3 the CPU->ANE flip lies in (1.416e8, 1.557e8) conv FLOPs, i.e. theta is
just above 1.4e8 and below 1.56e8. This corroborates API-147's ~1.5e8 gate and narrows it, using
an instrument (the SDK's own plan API) independent of the earlier route_sweep/decision table.

Caveat: the bracket is measured for C=256 conv3x3 only; a clean FLOPs law across kernel sizes
and channel counts is not established here, and the exact predicate (which per-device cost
quantity is compared) is still not recovered.

4. Is the gate conv FLOPs? NO - it is not a function of FLOPs alone
------------------------------------------------------------------
One-conv sweeps across (kernel k, channels C), square and non-square, order-of-execution
^ note: each row is a separate model, so "preferred" is read per model, not per size step.

  k=3 C=256   H=11        1.42737e8  CPU      |  k=5 C=128  15x12    1.47456e8  CPU
  k=3 C=256   H=12        1.69869e8  ANE      |  k=5 C=128  16x12    1.57286e8  ANE
  k=3 C=256   12x10(W)    1.41558e8  CPU      |  k=5 C=128  17x12    1.67117e8  ANE
  k=3 C=256   12x11(W)    1.55714e8  ANE      |  k=3 C=512  5x6      1.41558e8  CPU
  k=1 C=256   H=32        1.34218e8  CPU      |  k=3 C=64   45x45    1.49299e8  CPU
  k=1 C=256   H=34        1.51519e8  ANE      |  k=3 C=128  22x23    1.49225e8  CPU
  k=1 C=256   25x44       1.44179e8  CPU      |  k=5 C=256  10x11    3.60448e8  ANE
  k=1 C=256   25x45       1.47456e8  ANE      |
  k=1 C=256   25x43       1.40902e8  CPU      |  k=3 C=64   22x22    1.42737e8  CPU (see k=3 C=128 row)
  k=3 C=128   H=22        1.42737e8  CPU      |
  k=3 C=128   H=24        1.69869e8  ANE      |

COUNTEREXAMPLE at identical FLOPs (reproduced 3/3):
  k=1 C=256 25x45   1.47456e8 FLOPs  -> ANE
  k=5 C=128 15x12   1.47456e8 FLOPs  -> CPU

So `preferred` is NOT a function of conv FLOPs alone, and the earlier "~1.5e8 FLOPs gate"
(API-147) is at best a CORRELATE for the common configs measured, not the predicate.

What the data do support:
  * within ONE config, `preferred` is monotone in FLOPs (every series flips once, CPU -> ANE);
  * the flip FLOPs DIFFER per (k, C): k=1/C=256 flips at <=1.4746e8; k=5/C=128 needs >1.4746e8;
    k=3/C=64 is still CPU at 1.493e8; k=3/C=512 is still CPU at 1.4156e8;
  * the difference does not track weights or output count alone either:
      k=1/C=256/25x45  weights=65536    outputs=288000  -> ANE
      k=3/C=64/45x45   weights=36864    outputs=129600  -> CPU   (fewer weights, MORE outputs? no:
                                                                  outputs 129600 < 288000, but FLOPs higher)
    i.e. a per-op COST model with more inputs than FLOPs (weights, activations, shape) is at work;
    identifying it needs a designed experiment, not more sweep rows.

Method note: harness/plan_flip_sweep.sh drives this (`sh plan_flip_sweep.sh <k> <C> <H,H,...>`),
one model per row, decision read from the SDK plan API by plan_devicesupport.
